## 0. 리뷰어에게

당신은 시니어 프로덕트 엔지니어이자 추천 시스템 리뷰어다.
개인 개발자 한 명(진웅)이 만드는 관계 아카이브 앱의 **방향 전환**을 평가해달라.

**원하는 것**

- 방향 전환의 논리에 구멍이 있으면 지적. 특히 "이러면 안 될 것 같다"보다
  **"이 가정이 틀리면 무엇이 무너지는가"**
- 우리가 못 본 실패 모드
- 순서가 틀렸다면 그 근거
- 개인 프로젝트 규모에서 과설계인 부분

**원하지 않는 것**

- 일반론 ("사용자 인터뷰를 하세요", "MVP를 작게 하세요")
- 이미 아래 §4에 "버렸다"고 적힌 선택지의 재제안
- 코드 스타일·리팩터링 지적. 지금은 방향 리뷰다
- 칭찬. 동의하는 부분은 한 줄로 넘어가고 반대 지점에 분량을 써달라

**답변은 한국어로.**

### 제약

- Cloudflare Pages + D1. **Workers 무료 플랜은 요청당 CPU 10ms**, Pages Functions는 cron이 없다
- **카카오 로컬 API가 유료로 바뀌었다.** 진웅이 지금 자금을 쓰지 않기로 했다 (#22)
- 개인 프로젝트. 상업화 가능성은 열어두지만 지금은 무료 베타
- 자동 테스트 71개 통과 중

### 점수식 (설계만 됨, 미구현)

```
0.5 · min(A 만족도, B 만족도)  +  0.3 · √(A·B)  +  0.2 · synergy
```

`min` 항 때문에 **두 사람의 반응이 각각 있어야** 학습이 된다.
L0 졸업 조건은 추천 품질이 아니라 **로그 세션 100개**다.

## 3. 평가받으려는 것 — 방향 전환

### 원래 방향

상대에게 못 하는 말·비밀·취향을 "소곤파일"로 저장해두고,
**정해둔 날짜(기념일·크리스마스)에 상대 알림으로 열린다.**
그렇게 쌓인 취향으로 데이트 코스를 추천한다.

### 받은 피드백

> "이러면 연애 초반에만 쓸 것 같다."

### 우리가 진단한 원인 (구조 문제)

1. **저장할 게 고갈된다.** 비밀·취향은 초반에 몰려 있다
2. **보상이 너무 멀다.** 100일 뒤에 열린다면 그 사이 앱을 열 이유가 없다
3. **들어와도 볼 게 없다.** 내가 쓴 건 이미 알고, 상대가 쓴 건 못 본다
   — 이건 **절대 규칙 1**이라 고칠 수 없다

그리고 더 큰 문제를 따로 발견했다.

**소곤.zip이 두 개의 앱이었다** — *시한부 편지함*과 *데이트 추천기*.
둘이 공유하는 게 거의 없었다. **절대 규칙 2**가 `sogon_files.content`를
추천 입력에서 금지하므로, "비밀들을 합쳐 취향을 판단한다"는 원래 서사는
**규칙상 처음부터 불가능**했다.

### 전환 (ADR #20 · #21 · #22)

**#20 — 날짜를 1급 객체로 만들어 두 반쪽을 잇는다.**
잇는 건 본문이 아니라 **날짜**다. 그래서 절대 규칙 2를 안 깬다.
기념일도 주간 데이트도 같은 날짜 객체다. 소곤파일도 그날 열리고,
**데이트 코스도 미리 담아뒀다가 그날 연다.** 은유가 통일된다.

**#21 — "오늘의 질문"이 리텐션 엔진이자 취향 공급원이다.**
날짜가 정해지면 D-7부터 매일 하나씩 묻는다. 선택지마다 `(axis, tag, weight)`를
**코드에** 두어 결정론적으로 `preference_signals`를 만든다. LLM 없음.
(`IntroScreen`이 이미 "오늘의 질문"을 광고하는데 구현이 없었다.)

**#22 — 카카오 로컬 보류.** 유료다. 음식 축이 빈 채로 간다.

### 순서

```
0004 date_plans → 약속 등록 → 오늘의 질문 → 추천 생성·로깅 → 공유 반응
```

베타 오픈(친구 2~3커플)에 필요한 건 **약속 등록 + 오늘의 질문까지**.
추천 없이도 제품이 성립하고, 그 사이 취향이 쌓여야 추천이 무작위가 아니게 된다.

## 5. 우리가 이미 아는 약점

여기에 동의만 하는 답변은 가치가 없다. **이것들의 심각도 순위**나
**우리가 놓친 해법**이 있으면 그걸 말해달라.

1. **알레르기를 필터할 근거가 장소 쪽에 없다** (Q14). 메뉴 데이터를 주는 공개 API가
   없다. 절대 규칙 5는 알레르기를 하드 필터로 못박았는데 지금은 거를 수 없다.
   **물어보고 못 거르는 건 안 물어보는 것보다 나쁘다.** 예산·영업시간도 같은 구멍이라
   지금은 필터가 도는 척만 한다
2. **음식점 458개가 랭커 입장에서 거리 말고는 구분되지 않는다.** 카카오 보류의 대가
3. **미리 뽑은 코스는 그 사이 죽는다.** 30일 안에 224건이 끝난다
4. **실사용 커플 0쌍.** 1커플 주 1회면 세션 100개에 2년, 5커플이면 20주
5. **`00-product.md`의 "데이트 코스 앱이 아니다" 절이 #20과 긴장이 있다.**
   그 파일은 진웅만 고친다
6. 매일 답할 질문을 몇 개나 만들 수 있는지 검증 안 됨 (Q15)
7. 소곤파일과 코스를 한 화면에 놓으면 **절대 규칙 3**(열림은 항상 명시적)과
   부딪힐 수 있다 (Q16)

## 6. 답해줬으면 하는 질문

1. **"연애 초반에만 쓸 것 같다"의 진단(§3)이 맞나?** 우리가 원인을 셋으로 봤는데
   더 근본적인 게 있나. 예컨대 "1:1 비공개"라는 전제 자체가 리텐션과 양립 불가한가?

2. **날짜로 잇는 게 진짜 해결인가, 봉합인가?** 두 기능이 같은 날짜 위에 있다고
   해서 사용자가 하나의 제품으로 느낄까. 아니면 여전히 앱 두 개인가?

3. **"오늘의 질문"에 과부하가 걸려 있지 않나?** 리텐션 · 취향 데이터 · 온보딩 ·
   `min(A,B)` 학습을 하나가 다 짊어진다. 이게 실패하면 전부 무너지는데,
   실패 확률이 얼마나 되나. 무엇으로 헤지해야 하나?

4. **순서가 맞나?** 추천을 마지막에서 두 번째로 미뤘다. 그런데 추천이 이 제품의
   차별점이라면 늦추는 게 맞나? 반대로, 추천을 아예 접고 아카이브+질문만
   깊게 파는 게 나은가?

5. **알레르기(Q14)를 어떻게 다뤄야 하나?** 세 갈래를 적어뒀다 —
   (a) 안 묻는다 (b) 카테고리 수준만 거른다 (c) 입력받되 "확인 못 함"을 표시한다.
   넷째 길이 있나? 안전 약속과 제품 가치 사이에서 어디에 서야 하나?

6. **`0003_recommendation.sql`의 스키마가 이 방향을 감당하나?** 날짜가 1급 객체가
   되면서 `date_plans`를 0004에 추가하려 한다. 스키마를 보고 지금 방향에서
   빠진 필드나 잘못된 정규화가 있으면 지적해달라.

7. **개인 프로젝트 규모에서 과설계인 부분은?** 특히 추천 로그 3종
   (`recommendation_requests` / `_impressions` / `_feedback`)과
   `features_json` 보존. 사용자 0명인데 학습 파이프라인을 이만큼 준비한 게 맞나?
