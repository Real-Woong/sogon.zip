# 결정 기록 (ADR)

같은 논의를 세 번째로 반복하지 않기 위한 파일이다.
**설계를 바꾸려 하기 전에 여기부터 본다.** 뒤집어도 되지만, 뒤집을 때는 항목을
지우지 말고 `상태: 뒤집힘 → #번호`로 남긴다.

형식: 결정 / 이유 / 대신 포기한 것

---

## 1. 추천 수집과 서빙을 분리한다

**상태**: 확정 (2026-08-09)

요청마다 외부 API를 부르지 않는다. 배치로 긁어 D1에 정규화 저장하고, 요청 시엔 로컬만 읽는다.

**이유**: 5개 API × 300~800ms면 3초를 넘긴다. 무료 쿼터는 사용자 수에 비례해 터진다.
국내 지도/검색 API는 결과 저장에 약관 제한이 있다. 결정적으로 점수에 필요한 값(가격대,
분위기, 팝업 종료일)이 API 응답에 아예 없어서 어차피 보강이 필요하다.

**포기한 것**: 실시간성. 오늘 문 연 가게가 최대 하루 늦게 들어온다. 데이트 코스는
그 정도 지연이 문제되지 않는다고 판단했다.

---

## 2. 장소와 이벤트를 한 테이블(`places`)에 담는다

**상태**: 확정 (2026-08-09)

상시 맛집·카페와 기간 한정 팝업·전시를 나누지 않는다. `starts_at` / `ends_at`이 NULL이면 상시다.

**이유**: `recommendation_impressions`가 단일 `place_id`로 참조해야 하는데 SQLite에는
다형 외래키가 없다. 두 테이블로 나누면 로그마다 "어느 테이블의 id인가"를 들고 다녀야 하고,
학습 데이터 조인이 매번 UNION이 된다.

**포기한 것**: 이벤트 전용 컬럼의 명확함. `places`에 NULL이 많은 컬럼이 생겼다.

---

## 3. 학습은 오프라인, 서빙은 선형 결합

**상태**: 확정 (2026-08-09)

로지스틱 회귀 또는 pairwise LTR을 로컬/Colab에서 학습하고, **계수 JSON만 배포**한다.

**이유**: Workers 무료 플랜은 요청당 CPU 10ms다. 추론이 `sum(w*x)` 몇 줄이면 지연이
무시된다. 모델 배포가 파일 교체라 롤백도 쉽다. 피처가 20~40개 수준이라 딥러닝을 쓸
데이터가 애초에 안 모인다.

**포기한 것**: 온라인 학습. 모델 갱신이 수동 배치가 된다. 지금 규모에선 문제없다.

## 4. 피드백은 커플이 아니라 개인 단위로 받는다

**상태**: 확정 (2026-08-09)

`recommendation_feedback.member_id`는 NOT NULL이다.

**이유**: 점수식의 핵심이 `min(A 만족도, B 만족도)`다. 커플 단위로만 받으면 누가 만족했는지
알 수 없어서 이 항을 **영원히** 학습할 수 없다. 한쪽이 계속 희생하는 걸 잡는 게 이 제품이
풀려는 문제라서, 이걸 못 배우면 추천 기능의 존재 이유가 없어진다.

**포기한 것**: 입력 단순함. 화면에서 "우리 둘 다 좋았어요" 한 번으로 못 끝내고
누구의 반응인지 알아야 한다.

## 5. 추천 당시 피처를 `features_json`으로 통째로 저장한다

**상태**: 확정 (2026-08-09)

**이유**: 나중에 재계산하면 인과가 깨진다. 팝업이 끝나고 가격이 바뀐 뒤의 피처로
"그때 왜 저장했는가"를 학습하면 틀린 걸 배운다.

**포기한 것**: 저장 공간. 노출마다 JSON이 하나씩 쌓인다. D1 용량이 문제되면
오래된 로그를 집계 후 아카이브한다.

## 6. `places`는 물리 삭제하지 않는다

**상태**: 확정 (2026-08-09)

`DELETE /api/admin/places/:id`는 `status='closed'`로 바꾼다.

**이유**: 노출 로그가 참조하고 있고 그게 학습 데이터다. 끝난 팝업을 지웠다고
과거 추천 기록이 사라지면 안 된다. 병합으로 지는 쪽도 마찬가지로 닫기만 한다.

---

## 7. 중복 병합은 50m 자동 / 2km 사람 판단

**상태**: 확정 (2026-08-09)

정규화 상호가 같고 50m 이내면 같은 장소로 보고 409를 돌려준다.
같은 상호가 2km 이내에 있으면 `place_merge_reviews`에 쌓고 운영자가 판단한다.

**이유**: 완전 자동 병합은 "성수점"과 "성수 2호점"을 합쳐버린다. 반대로 병합을 안 하면
같은 팝업이 두 번 추천된다. 둘 다 신뢰를 잃는다. 애매한 구간만 사람이 본다.

**미검증**: 50m와 2km는 감으로 정한 값이다. 실제 데이터 200건쯤 넣어보고 조정한다.
(→ 아직 미검증. `05-open-questions.md` Q13)

**보강 (2026-08-10)**: 거리만으로는 부족했다. 병합 키에 **기간 겹침**이 세 번째 축으로
들어갔다. 같은 극장에서 다음 달에 올리는 다른 공연은 같은 이름·같은 좌표여도
다른 것이다. #15를 본다.

## 8. 후보 생성은 항상 지오해시 이웃 9칸을 조회한다

**상태**: 확정 (2026-08-09)

`geohashWithNeighbors()`를 거치지 않고 `geohash5 = ?`로 조회하는 코드를 만들지 않는다.

**이유**: 셀 하나만 보면 경계 바로 건너편 수십 m 거리의 장소가 후보에서 통째로 빠진다.
증상이 "추천이 좀 이상하다" 정도로만 나타나서 발견이 아주 늦다.
`scripts/test.mjs`가 ±4km 격자를 훑어 이걸 검증한다.

## 9. 운영자 권한은 API로 승격시키지 않는다

**상태**: 확정 (2026-08-09)

가입은 항상 `role='member'`다. `admin`으로 올리려면 D1에서 직접 UPDATE 한다.
`requireAdmin`은 권한 없으면 403이 아니라 **404**를 준다.

**이유**: 승격 API가 있으면 그게 곧 권한 상승 공격면이다. 운영자가 한 명인 동안은
수동이 가장 사고가 적다. 404를 주는 건 운영자 경로의 존재 자체를 알리지 않기 위해서다.

## 10. 하드 제약은 학습 대상이 아니다

**상태**: 확정 · 절대 규칙 (`00-product.md` 참조)

알레르기, 영업시간, 예산 상한, 최대 이동시간은 필터다. 가중치로 상쇄되지 않고
LLM이 판정하지 않는다. `preference_signals.is_hard_constraint = 1`로 분리 저장한다.

**이유**: 학습된 점수는 확률적이라 "가끔 뚫린다". 알레르기가 가끔 뚫리면 제품이 아니라 사고다.

## 11. CLI 도구는 devDependency로 고정한다

**상태**: 확정 (2026-08-09)

`wrangler`를 `package.json`에 넣고 `yarn wrangler ...`로 부른다.
전역 설치나 `npx` / `yarn dlx`를 문서에 적지 않는다.

**이유**: `BETA_DEPLOY.md`가 처음부터 `wrangler d1 execute ...`를 안내하고 있었는데,
그 도구는 전역에도 프로젝트에도 설치된 적이 없었다. 문서를 믿고 명령을 실행하면 실패하고,
사람과 에이전트 양쪽이 매번 환경부터 디버깅하게 된다. 버전이 고정돼야 어제 되던 명령이
오늘도 된다.

**포기한 것**: 설치 용량(약 200MB)과 `yarn.lock` 변경. `@cloudflare/workers-types`도
wrangler의 peer 요구(`^5.20260801.1`)에 맞춰 5.20260808.1로 함께 올렸다.

**따라오는 규칙**: 문서에 명령을 적을 때는 그 도구가 `package.json`에 있는지 먼저 확인한다.

## 12. 프리뷰 환경은 당분간 쓰지 않는다 (검증은 프로덕션에서)

**상태**: 보류 — 프로토타입 + 추천 시스템이 완성되면 다시 켠다 (2026-08-09)

Cloudflare Pages는 바인딩을 Production / Preview 환경별로 **따로** 관리한다.
지금 `DB` 바인딩은 Production에만 걸려 있고, **Preview에는 일부러 걸지 않는다.**
따라서 프리뷰 배포에서는 DB를 쓰는 모든 엔드포인트가 500이다. 이건 버그가 아니다.
PR은 머지 전 검증 없이 main으로 보내고, 프로덕션 배포에서 확인한다.

**이유**: 아직 실사용자가 0명이라 프로덕션에서 깨져도 다치는 사람이 없다.
반대로 프리뷰를 제대로 쓰려면 DB·계정·마이그레이션을 두 벌 유지해야 하는데,
지금 속도에서는 그 비용이 얻는 안전보다 크다.

**언제 뒤집나**: 실사용자가 붙거나, 남이 못 볼 데이터가 프로덕션에 쌓이기 시작하면
그때는 프리뷰 없이 머지하는 게 위험해진다. 그 시점에 이 항목을 뒤집는다.

**발견 경위**: 첫 프리뷰 배포에서 로그인이 **존재하지 않는 계정에도** 500을 냈다.
`wrangler pages deployment tail`로 보니
`TypeError: Cannot read properties of undefined (reading 'prepare')` —
`env.DB`가 undefined였다. 라우팅 자체는 정상이었다
(`/api/admin/places`가 404가 아니라 401을 돌려줬다).

**남겨둔 것**: `sogonzip-db-preview` (`e83079e6-366c-478b-8ee0-55bbad7a4586`)를
이미 만들어 0001~0003을 적용하고 운영자 계정을 넣어뒀다. 나중에 켤 때 바로 쓴다.

⚠️ **이 DB는 지금부터 스키마가 뒤처진다.** 0004 이후 마이그레이션은 여기에 적용되지
않는다. 나중에 켤 때는 **누락된 마이그레이션을 먼저 채우고** 바인딩한다.
그냥 붙이면 "프로덕션에선 되는데 프리뷰에선 안 되는" 유령 버그를 쫓게 된다.

**켤 때 할 일**: 대시보드 → Pages → sogon-zip → Settings → Bindings의 **Preview**
환경에 `DB` = `sogonzip-db-preview` 추가. 바인딩은 **다음 배포부터** 적용되므로
추가 후 반드시 재배포한다.

## 13. 데이터는 공공 API로 만들고, 팝업만 사람이 보강한다

**상태**: 확정 (2026-08-09) · 근거 문서
[`../reference/data/date-course-data-strategy.md`](../reference/data/date-course-data-strategy.md)

Q1(팝업 데이터)과 Q4(서비스 지역)를 함께 닫는다.

**서비스 지역**: 서울 핵심 상권 6곳 — 성수 · 한남 · 연남/홍대 · 을지로 · 잠실 · 강남/신사.
전국을 넣으면 밀도가 낮아 "도보 12분" 같은 코스가 애초에 안 나온다.

**소스를 역할별로 나눈다.** 하나의 완벽한 API를 찾지 않는다.

| 역할 | 소스 |
|---|---|
| 행사·전시 기본 | 서울 문화행사, TourAPI, KOPIS |
| 맛집·카페 장소 | 카카오 로컬 |
| 신규 팝업 발견 | 다음 웹·블로그 검색 |
| 사실 확인 | 공식 홈페이지·예약 페이지 |
| 롱테일 | 운영자 직접 등록 (`/api/admin/places`) |

**Instagram 화이트리스트는 1단계에서 뺀다.** 전략 문서는 100~300개 계정 감시를 1단계에
넣었지만, 공식 API로는 일반 계정을 읽을 수 없어 결국 스크래핑이 된다. 문서 스스로 §2에서
그게 깨지기 쉽다고 적어놨다. 공공 API로 먼저 밀도를 만들고 무엇이 부족한지 눈으로 본 뒤에
다시 판단한다.

**포기한 것**: 초기 팝업 커버리지. 팝업은 검색 발견 + 수동 입력으로만 들어오므로 한동안 얇다.

**실데이터로 수정한 것 (2026-08-10)**: "상권 6곳 바깥은 저장하지 않는다"를 뒤집었다.
서울 문화행사 19,488건 중 **아직 안 끝난 건 403건뿐이었다.** 상권 6곳 반경 1.5km로
자르면 84건만 남는다. 403건은 저장 비용이 사실상 0인데(D1 0.26MB) 버리면 319건이 사라진다.
**밀도는 저장 단계가 아니라 추천 시점의 지오해시 후보 생성에서 잡는 게 맞다.**

→ 서울 전체를 저장하고, 상권은 `area_code`로 표시만 한다. 반경은 2000m(도보 25분)로
   잡았다. 1500m면 84건, 3000m면 걸어서 40분이라 더는 상권이 아니다.

→ 상권에 **종로·삼청 / 대학로 / 명동·충무로**를 추가했다. 원래 6곳에 없었는데 종로가
   단독 1위였다(80건). 광화문·삼청동·인사동은 실제로 사람들이 데이트하는 곳이다.

**스키마는 지금 건드리지 않는다.** 전략 문서가 요구하는 `verified_at` / `expires_at`(재확인
기한) / `official_url` / `source_url` / `sold_out` 상태가 아직 없다. 하지만
`place_sources.raw_json`에 원본 응답을 통째로 저장하므로 **재검증을 실제로 구현할 때
0004에서 backfill하면 된다.** 쓰지도 않을 컬럼을 미리 만들지 않는다.

**미정**: 장소 태그 표현. 전략 문서는 가중치 축(`{mood: {emotional: 0.9}}`)을 쓰는데
`places.tags_json`은 평평한 배열이다. 실제 태깅을 시작할 때 정한다.

## 14. TourAPI는 KorService2 + 디코딩한 키로 부른다

**상태**: 확정 (2026-08-10)

두 가지를 틀리면 각각 400과 403이 나는데, 응답만 봐서는 원인을 알 수 없다.
`scripts/ingest/tourApi.mjs` 상단에도 적어뒀다.

1. **`KorService1`은 폐지됐다.** 같은 파라미터로 400을 낸다. `KorService2`를 쓴다.
2. **공공데이터포털이 주는 키는 이미 URL 인코딩된 상태다.** 그대로 쿼리에 넣으면
   이중 인코딩돼서 403이 난다. `decodeURIComponent`를 한 번 거쳐야 한다.

**수집 범위**: contentTypeId 12(관광지) · 14(문화시설) · 28(레포츠) · 38(쇼핑) ·
39(음식점). 39는 `cat3 === 'A05020900'`이면 카페, 아니면 음식점이다.

**뺀 것**:
- 15 축제공연행사 — 이 조회로는 **행사 기간이 안 나온다.** 종료일 없이 넣으면
  끝난 행사를 추천하게 된다. 서울 문화행사가 이미 덮고 있다.
- 25 여행코스 — 장소가 아니라 코스다. 코스는 우리가 만든다.
- 32 숙박 — `05-open-questions.md` Q12.

**비워둔 것**: 가격대와 영업시간. 이 조회에 없고 소개정보조회(`detailIntro2`)를
콘텐츠마다 한 번씩 더 불러야 하는데 개발계정 트래픽이 하루 1000이다.
NULL은 "미상"이라 예산·영업시간 하드 필터에서 제외되지 않는다.

## 15. 병합 키는 이름 + 좌표 + 기간 겹침. 괄호 안은 지우지 않는다

**상태**: 확정 (2026-08-10) — `05-open-questions.md` Q5를 닫는다

실데이터 1,364건에서 나온 버그다. `normalizePlaceName`이 괄호 안을 전부 지웠는데
서울 문화행사 제목은 `[주최기관] 제목 [작품명]` 형식이라 괄호가 오히려 정체성이었다.

```
[세종문화회관] 뮤지컬 [베토벤]          → "뮤지컬"
[중구문화재단] 뮤지컬 [디어 에반 핸슨]   → "뮤지컬"   ← 같은 장소로 판정
```

두 가지를 바꿨다.

1. **괄호 안 글자를 남긴다.** 지우는 건 지점 표기(`(성수점)`, `(2호점)`)뿐이다.
2. **병합 키에 기간 겹침을 넣는다.** `dateRangesOverlap`. 기간이 없는 쪽은 상시
   운영으로 보고 항상 겹치는 것으로 친다. 전략 문서 §4가 처음부터 요구하던 것이다.

**왜 "괄호가 이름의 대부분이면 남긴다" 같은 비율 규칙을 안 썼나**: 처음엔 그렇게
짰는데 실데이터에서 6건이 안 잡혔다. `[세종문화회관] 세종예술아카데미 [박인홍 작가]
스테들러와 함께하는 여행드로잉 클래스`는 괄호 밖이 길어서 비율 조건을 통과해버린다.
괄호가 부연인지 정체성인지 기계적으로 구분할 방법이 없다.

**남겨도 손해가 적은 이유**: 괄호 문자 자체는 마지막 구두점 제거에서 사라진다.
`블루보틀 (성수)`와 `블루보틀 성수`는 어차피 같은 키가 된다. 한쪽 소스가 괄호
부분을 **통째로 빠뜨렸을 때만** 갈라진다. 실데이터에 그런 쌍이 하나 있다
(`공근혜갤러리` / `[K드라마 촬영지] 공근혜갤러리`). 오탐 11건을 없애고 미탐 1건을
얻는 거래라 받았다. 미탐 쪽 대책은 Q13에 적어뒀다.

**포기한 것**: 종류(`kind`)를 병합 키에 넣는 것. 같은 자리의 카페와 음식점은
대개 같은 가게다. 넣으면 갈라진다.

**결과**: 프로덕션 병합 키 충돌 12건 → 0건. 409 오탐이 사라졌다.

## 16. 파생 값 backfill과 만료 정리는 스크립트로 둔다

**상태**: 확정 (2026-08-10)

- `scripts/ingest/renormalize.mjs` — `name_normalized`를 현재 규칙으로 다시 계산한다.
  **`normalizePlaceName`을 고칠 때마다 돌려야 한다.** 병합 키는 계산해서 넣어둔
  값이라, 규칙만 바꾸면 이미 들어간 행은 낡은 키를 들고 있고 새 장소가 옛 키와
  비교된다. #15를 적용하면서 409건을 갱신했다.
- `scripts/ingest/closeExpired.mjs` — `ends_at`이 지난 `active` 장소를 `closed`로
  바꾼다. 매일 한 번. 수집기는 끝난 행사를 새로 넣지 않지만, 넣을 때 살아 있던
  행사는 시간이 지나도 `active`로 남는다.

**되돌리지 않는다**: 종료일이 미뤄져 다시 살아난 행사를 자동으로 열면, 운영자가
손으로 닫은 장소(`DELETE /api/admin/places/:id`도 `closed`를 쓴다)까지 되살아난다.
다시 여는 건 사람이 한다.

**wrangler의 변경 행 수는 믿지 않는다**: `d1 execute --file --json`이 주는
`meta.changes`는 실제 행 수보다 크다(1행짜리 UPDATE에 2가 온다). 두 스크립트 모두
실행한 뒤 다시 SELECT해서 확인하고, 어긋나면 실패로 끝낸다.

**후속 결정**: 만료 누락 위험 때문에 로드맵 9번을 앞당겨 Cron Worker로 옮겼다(`#25`).
Pages Functions는 cron을 못 돌리고 요청당 CPU가 10ms라 별도 Worker로 분리했다.

## 17. 로그인·연결 상태로 라우트를 가른다. 프로필의 단일 소스는 세션이다

**상태**: 확정 (2026-08-10)

진웅이 잡았다. 다솜은 원우와 이미 연결돼 있는데 로그인 후에도 "연인 찾기"가 계속 나왔다.

원인은 두 가지였고 둘 다 고쳤다.

**1. 계정 만들기 전 화면에 가드가 없었다.** `RedirectIfAuthed`가 걸린 건 `/login`
하나뿐이라, 로그인한 사람이 주소창으로 사이트에 다시 들어오면 `/`(소개) →
`/relationship`("연인과 시작하기") → `/create-room`을 그대로 만났다.

→ `/`, `/intro`, `/relationship`, `/login`은 `RedirectIfAuthed`로 감싼다.
→ `/create-room`은 `RedirectIfConnected`로 감싼다. 여기는 비로그인(가입)과
   로그인했지만 미연결(연결 코드 입력) 둘 다 들어와야 해서 `RedirectIfAuthed`를
   쓸 수 없다. **이미 연결된 사람만** 홈으로 보낸다. 정원이 2명이라 더 할 게 없다.

**2. `syncRemoteData()`가 프로필을 갱신하지 않았다.** 파일과 취향만 받아왔다.
`HomeScreen`은 `syncRemoteData()` 뒤에 `getProfile()`을 다시 읽었는데, 그 함수는
localStorage를 읽을 뿐이라 값이 그대로였다. **상대가 연결을 수락해도 새로고침
전까지 "아직 누구와도 연결되지 않았어요"가 남는다.**

→ 화면이 프로필을 따로 들고 있지 않는다. `useSession()`이 단일 소스다.
   `HomeScreen`은 진입할 때 `refresh()`를 불러 서버에 다시 물어본다.

**따라오는 규칙**: 화면에서 `getProfile()`을 `useState` 초기값으로 쓰지 않는다.
연결 상태는 상대의 행동으로 바뀌기 때문에, 내 기기의 마지막 스냅샷은 언제든 낡았다.

## 18. 베타 추천은 친구 2~3커플에게 "실험 중"으로 연다

**상태**: 확정 (2026-08-10) — `05-open-questions.md` Q2를 닫는다

진웅 결정. 실사용 커플을 2~3쌍 모집하고, 품질이 낮다는 걸 미리 알리고 연다.

**이유**: L0 졸업 조건이 추천 품질이 아니라 **로그가 쌓이는 것**이다. 품질이
좋아질 때까지 기다리면 로그가 안 쌓이고, 로그가 없으면 품질이 안 올라간다.
기다리는 선택지는 교착이다.

**산수**: 세션 100개가 목표다. 1커플 주 1회면 2년, 5커플이면 20주다.
지금 실사용 커플은 0쌍이므로(다솜·원우는 진웅의 테스트 계정) **사람을 붙이는 것
자체가 데이터 수집의 첫 단계다.** 파이프라인을 아무리 잘 만들어도 0이 쌓인다.

**따라오는 제품 요구사항**: 점수식의 `min(A 만족도, B 만족도)`는 두 사람 반응이
모두 있어야 계산된다. 지금처럼 추천을 요청한 사람만 반응하면 이 항을 영원히
못 배운다(#4). 추천은 개인의 목록이 아니라 **소곤폴더에 놓이는 공유 객체**여야
한다 — A가 코스를 뽑으면 B의 홈에 뜬다. `recommendation_requests.room_id`가
이미 있어서 스키마 변경은 없다.

## 19. 사람 쪽 데이터보다 장소 쪽 속성이 먼저다 (온보딩을 뒤로 미룬다)

**상태**: 확정 (2026-08-10) — Q3의 순서를 정한다

원래 취향 온보딩(2지선다)을 먼저 만들려고 했다. 적재된 1,364건의 실제 필드를
세어보고 뒤집었다.

| 필드 | 실태 |
|---|---|
| 음식점 458 + 카페 107 | 태그가 `"음식점"` 하나뿐. 한식/양식/매운맛 구분 없음 |
| `price_level` | 음식점·카페 전부 NULL. 있는 건 activity 268 / exhibition 95 |
| `opening_hours` | 1,364건 전부 없음 |
| 분위기(조용한/활기찬) | 없음 |

**취향을 물어봐도 매칭할 필드가 장소 쪽에 없다.** 458개 음식점은 랭커 입장에서
거리 말고 구분되지 않는다. 온보딩을 먼저 만들면 신호는 쌓이지만 쓸 데가 없다.

→ **카카오 로컬이 먼저다.** `category_name`이 `음식점 > 한식 > 육류,고기` 형태라
   그게 곧 음식 축이다. 카카오의 값어치는 장소 개수가 아니라 **속성**에 있다.

**지금 매칭 가능한 축** (온보딩 없이도 규칙 기반 추천이 도는 범위):
종류(kind) · 실내외 · 장르 태그(전시/클래식/연극/교육체험/레포츠…) ·
무료 여부(253건) · 지역(area_code) · 기간.
"전시 + 카페 + 공원" 같은 코스는 이걸로 나온다.

**따라서 순서**: 카카오 → 추천 생성·로깅 → 온보딩 → 공유 UX.
추천 생성·로깅은 카카오에 의존하지 않으므로 활성화를 기다리는 동안 진행한다.

## 20. 날짜가 1급 객체다. 소곤파일과 데이트 코스가 같은 날짜 위에 놓인다

**상태**: 확정 (2026-08-10) · 진웅 결정 — #19의 순서를 대체한다

**받은 피드백**: "이러면 연애 초반에만 쓸 것 같다."

마케팅 문제가 아니라 구조 문제였다. 원인이 셋이다.

1. **저장할 게 고갈된다.** 비밀·취향은 초반에 몰려 있다
2. **보상이 너무 멀다.** 100일 뒤에 열린다면 그 사이 앱을 열 이유가 없다
3. **들어와도 볼 게 없다.** 내가 쓴 건 이미 알고, 상대가 쓴 건 못 본다(절대 규칙 1)

세 번째는 고칠 수 없고 고쳐서도 안 된다. **제품의 핵심 규칙이 곧 리텐션의 적이다.**

그리고 더 큰 문제가 따로 있었다. **소곤.zip이 두 개의 앱이었다** —
시한부 편지함과 데이트 추천기. 둘이 공유하는 게 거의 없었다.
절대 규칙 2가 `sogon_files.content`를 추천 입력에서 금지하므로
"비밀을 합쳐 취향을 판단한다"는 원래 서사는 **규칙상 이미 불가능**했다.

**결정**: 두 반쪽을 **날짜**로 잇는다. 본문이 아니라 날짜다. 규칙 2를 안 깬다.

- 기념일·크리스마스는 특별한 날짜, 주간 데이트는 반복되는 날짜일 뿐이다
- 소곤파일도 그날 열리고, **데이트 코스도 미리 담아뒀다가 그날 연다**
- 은유가 통일된다 — 파일/폴더/압축의 "정해둔 날에 연다"가 코스에도 적용된다

**추천은 소곤파일 열림에만 묶지 않는다.** 커플은 주기적으로 데이트하고, 주마다
날짜를 정해두는 사람도 많다. 그 날짜를 등록하면 코스를 미리 리스트업해둔다.

**이 결정이 푸는 것**: 열림에만 묶으면 사용 빈도가 1년에 몇 번으로 떨어져
세션 100개(L0 졸업)가 사실상 도달 불가능했다. 주 1회 데이트면 주 1회 세션이고,
5커플이면 20주다.

**포기한 것**: 즉흥성. "지금 당장 어디 갈까"는 이 제품의 질문이 아니다.
그건 카카오맵·네이버가 이미 잘한다. 우리는 **정해둔 날을 준비하는** 쪽이다.

## 21. "오늘의 질문"이 리텐션 엔진이자 취향 데이터 공급원이다

**상태**: 확정 (2026-08-10) — Q3(온보딩)을 흡수한다

`IntroScreen`의 3번째 슬라이드가 이미 "오늘의 질문"을 광고하고 있다.
**구현은 없다.** 파는 것과 있는 것이 다른 상태였다.

**날짜가 정해지면 그날까지 카운트다운하며 묻는다.** D-7부터 매일 하나씩.

구멍 넷을 하나로 막는다.

| 구멍 | 어떻게 막히나 |
|---|---|
| 저장할 게 고갈된다 (#20) | 매일 하나씩 공급된다 |

| 온보딩 2지선다 제작 비용 (Q3) | 따로 만들 필요가 없다 |

**점수식과의 정합**: 두 사람이 같은 질문에 **각자** 답하므로
`min(A 만족도, B 만족도)`의 양변이 실제로 채워진다 (#4). 추천 피드백보다
빨리 쌓이고, 질문이 왜 필요한지도 사용자에게 설명된다 —
"이 답이 토요일 코스에 들어가요."

**외부 API 비용 0원.** 카카오 로컬이 유료로 바뀌어 보류된 상황에서(#22)
돈을 안 쓰고 취향 축을 만드는 유일한 길이다.

## 23. 오늘의 질문 답은 최신 이진 신호로 저장하고, 과거 의미는 스냅샷으로 남긴다

**상태**: 확정 (2026-08-10) — `0004` 구현

7개 문항은 D-7부터 D-1까지 하나씩 연다. 각 문항의 두 선택지는 같은
`(axis, tag)`를 공유하고 `weight`만 `+1 / -1`로 둔다. 답할 때 `preferences`에
사람이 읽을 수 있는 문장을 남기고, `preference_signals`의 같은 축·태그는 최신 답으로
upsert한다. 동시에 `date_question_answers`에는 당시 `question_id / option_id / axis /
tag / weight`를 스냅샷으로 보존한다.

**이유**: 선택지마다 서로 다른 양수 태그를 계속 쌓으면 한 사람이 지난주에는 실내,
이번 주에는 야외를 골랐을 때 둘 다 선호하는 것으로 남는다. 이진 축의 최신 선택으로
두면 지금 약속의 의도를 바로 쓸 수 있다. 반대로 코드 문항만 믿으면 문구·매핑을 고친
뒤 과거 답의 뜻이 바뀌므로 학습 기록은 별도로 고정해야 한다.

**답 수정은 허용하지 않는다**: 한 약속의 같은 문항은 한 번만 답한다. 수정 UX와
신호 이력 병합은 베타에 불필요한 복잡도라 뺐다. 다음 약속에서 같은 축에 다시 답하면
최신 신호가 갱신된다.

**Q15는 닫지 않는다**: 약속 등록 최대 기간은 아직 강제하지 않는다. 먼 날짜는 저장만
되고 D-7 전에는 질문이 나오지 않는다. 실제 사용 부담을 보기 전에 4주 상한을 코드로
확정하지 않는다.

**약속이 겹치면 가장 가까운 하나를 묻는다**: 오늘의 질문은 하루에 하나라는 약속을
지킨다. 7일 안에 약속이 여러 개면 가장 가까운 약속부터 질문하고, 뒤 약속은 남은
날짜에 해당하는 문항부터 시작한다. 겹친 약속마다 전 문항을 채우는 것보다 일일 부담을
고정하는 쪽을 택했다.

**포기한 것**: 장기 누적 평균. L0에서는 개인의 오래된 성향보다 이번 약속을 준비하며
고른 최신 답을 우선한다. 누적 학습이 필요해지면 `date_question_answers` 원본으로
오프라인에서 다시 만들 수 있다.

## 25. `closeExpired`를 추천 생성보다 먼저 독립 Cron Worker로 자동화한다

**상태**: 확정 (2026-08-10)

로드맵 9번의 첫 배치 Worker를 추천 생성보다 먼저 만든다. `sogonzip-close-expired`가
프로덕션 D1을 직접 바인딩하고, 매일 한국 시간 03:05(UTC 18:05)에 종료일이 지난
`active` 장소를 `closed`로 바꾼다. Pages 요청 경로에는 이 작업을 넣지 않는다.

**이유**: 30일 안에 224건이 만료되는데 수동 실행을 빠뜨려도 에러가 나지 않는다.
그 상태로 추천 생성을 먼저 열면 죽은 장소가 조용히 후보에 남는다. 달력 시간에 따라
계속 생기는 데이터 부패라 기능 순서와 무관하게 먼저 자동화해야 한다. Pages Functions는
Cron Trigger를 지원하지 않고 무료 플랜 요청 경로의 CPU 예산도 작으므로 별도 Worker가 맞다.

**실행 방식**: 인덱스가 있는 `(status, ends_at)` 조건으로 후보 수를 세고, 단일 UPDATE 뒤
같은 조건을 다시 세어 검증한다. 장소별 JavaScript 루프는 돌지 않는다. 완료 로그에는
후보·성공·실패 건수를 구조화해서 남긴다. 잔여 행이나 D1 오류가 있으면 오류 로그를 남기고
예외를 다시 던져 Cron 재시도를 허용한다. `active → closed` 조건이라 중복 전달도 멱등적이다.

**시간 선택**: 서울 문화행사의 날짜형 종료일은 한국 시간 하루 끝으로 저장된다. 마지막 날
운영 중인 장소를 너무 일찍 닫지 않으면서 다음 날 추천 전에는 반영되도록 03:05를 택했다.

**포기한 것**: 수집기 전체를 한 번에 Worker로 옮기는 것. 서울·TourAPI 수집은 외부 호출과
큰 입력 처리가 있어 이번 10ms 경로에 함께 넣지 않는다. 기존 수동 스크립트는 Cron 장애 때의
복구 수단으로 남긴다.

## 26. 취향 온보딩을 만들었다가 접는다 — 코스가 온보딩을 대신한다

**상태**: 접힘 (2026-08-11). **프로덕션에는 적용된 적이 없다.**

Q3(#21의 "온보딩 안 만든다")을 뒤집고 필수 6 + 선택 10문항, member 스코프
`onboarding_answers`, 첫 사용 직전 게이트까지 만들어 테스트를 통과시켰다.
같은 날 되돌렸다. 기록으로 남기는 이유는 **왜 틀렸는지가 다음 설계의 근거**이기
때문이다.

**틀린 이유**: 문항이 전부 *속성*을 물었다 — 음식 종류, 실내외, 분위기.
그건 후보를 **순위 매기는** 문제의 입력이다. 그런데 이 제품이 만들려는 건
"12:00~21:00을 어떻게 보낼까"이고, 그건 **일정을 짜는** 문제다. 일정을 짜는 데
필요한 입력은 취향이 아니라 그날의 설정이다 — 언제, 어디서, 얼마.

실제로 필수 6개를 지금 데이터에 대보면 절반이 죽어 있었다. 이동 거리는 출발지를
저장하는 데가 없어 계산이 안 되고, 분위기는 장소 쪽 대응 데이터가 0이고,
실내외는 `is_indoor`가 실측이 아니라 `kind`에서 유도한 값이라 종류 문항과 중복이다.
**답이 후보 집합을 바꾸는 문항은 동네·종류·음식 계열 셋뿐이었다.**

**대신 하는 것**: 시간 창·동네·예산을 `date_plans`에 붙이고(`0005`), 시간표를
먼저 보여준 뒤 슬롯 교체로 취향을 배운다. "당신은 팝업을 좋아합니까"보다
"이 팝업 말고 다른 거"가 구체적이고, 맥락이 있고, 거짓말할 이유가 없는 신호다.

**#21은 다시 유효하다.** 취향은 오늘의 질문이 계속 모은다. 다만 #21이 놓친
"가입~연결 구간이 비어 있다"는 문제는 설문으로 메우지 않는다 — 그 구간에서
정말 필요한 건 두 번째 사람이고, 답은 연결을 쉽게 만드는 것이다.

**버린 것**: `0005_onboarding.sql`, `shared/onboardingQuestions.ts`,
`/api/onboarding`, 온보딩 화면, 라우트 가드. Git 기록에 남아 있다.

## 27. 하루 코스는 "시간 골격 → 슬롯 채우기" 두 단계로 만든다

**상태**: 1단계 확정 (2026-08-11) — `shared/dateCourseSkeleton.ts`

"12:00~21:00"을 받아 `점심 → 이동 → 활동 → 카페 → 이동 → 활동 → 저녁 → 여유`
같은 **빈 칸**을 먼저 만든다. 어떤 장소를 넣을지는 그다음이다.

**왜 나눴나**:
1. 골격은 **장소 데이터가 하나도 없어도** 완성하고 테스트할 수 있다. 영업시간이
   1,364건 전부 NULL인 지금, 이 절반은 먼저 끝내둘 수 있다.
2. 순수 함수라 Cron Worker와 화면이 같은 결과를 낸다. "미리 만든 코스"와
   "지금 다시 계산한 코스"의 시간표가 어긋나면 안 된다.

**식사는 시계에 못 박는다.** 점심은 11:30~13:30 사이에서만 시작하고, 저녁은
창의 **끝에서 역산**해 40분 여유를 남긴다. 점수만 보고 배치하면 15시에 점심을
넣는 코스가 나오는데, 아무리 좋은 식당이어도 그건 사람이 쓰는 일정표가 아니다.

**서비스 시간대(08:00~23:00)는 임시 가정이다.** 영업시간이 전부 NULL이라
"새벽 2시에 문 연 카페"를 걸러낼 방법이 없다. 이 상수가 없으면 00:00~12:45 창에
02:15 카페가 들어간다. 실제 영업시간이 채워지면 후보 단계의 하드 필터가 대신한다.

**날씨는 하루가 아니라 시간대로 판정한다.** 오후에만 비가 오는 날에 오전 산책까지
죽이면 안 된다. 그리고 **필터가 아니라 힌트다** — 산책 슬롯만 종류를 실내로 바꾸고
나머지는 `preferIndoor`만 세운다. 비 온다고 후보를 0개로 만들면 코스가 안 나온다.
예보 입력은 `HourlyWeather`라는 자체 형태로 받는다. 특정 제공자의 응답 모양을
골격 로직이 알면 제공자를 바꿀 때 여기까지 고쳐야 한다.

**"구멍 없음"은 회귀 테스트로만 지킬 수 있다.** 손으로 확인한 6개 케이스는 전부
멀쩡했는데, 전수 검사에서 2,046개 창 중 **481개**가 깨져 있었다(꼬리 유실,
앵커 앞 구멍, 첫 후보가 안 맞으면 나머지 종류를 안 시도하는 `break`).
`scripts/test.mjs`가 모든 시간 창을 훑어 슬롯이 빈틈없이 이어지는지 검사한다.

**포기한 것**: 자정을 넘는 창. 날짜가 두 개라 `date_plans` 한 행으로 표현되지
않고 영업시간 판정도 달라진다(Q12와 같은 이유).

## 28. 장소의 성격은 소스 원문이 아니라 통제된 어휘로 저장한다

**결정.** 두 수집 소스가 주는 분류를 `shared/placeFacets.ts`의 한 어휘로 접어서
`tags_json`에 `genre:art` 같은 **접두사 붙은 패싯**으로 넣는다. 소스 원문 라벨은
지우지 않고 표시용으로 남긴다. 컬럼은 새로 만들지 않는다.

**왜.** 로드맵 7번은 "TourAPI 961건의 `tags_json`이 `kind`와 중복이라 정보량이 0"이
문제라고 적혀 있었다. 실제로 보니 그건 증상이고, 진짜 문제는 **두 소스가 서로 다른
말을 쓴다**는 것이었다. TourAPI는 "미술관/화랑", 서울 문화행사는 "전시/미술"이라고
부르는데 둘은 같은 걸 가리킨다. 원문 그대로 두면 슬롯을 채울 때 둘이 영영 만나지
않는다. 서울 문화행사 403건은 이미 태그가 충실했는데도(무료 여부까지 있었다)
TourAPI와 조인이 안 되니 반쪽이었다.

**접두사를 쓰는 이유.** 기계가 매칭하는 값과 사람이 읽는 값을 한 배열에 같이 둘 수
있다. `["genre:art", "fee:free", "전시/미술", "무료"]`처럼. 컬럼을 나누면
마이그레이션이 필요하고, 나누지 않으면 `LIKE '%"genre:art"%'`로 조회하게 되는데
1,365건 규모에서는 그게 더 싸다. 커지면 그때 컬럼으로 옮긴다.

**모르는 코드에는 태그를 붙이지 않는다.** 25건이 그렇게 남았다 —
원문이 이미 "기타"인 게 19건, 데이트 장소가 아닌 것(학교·외국문화원·문화전수시설)이
6건이다. 억지로 어딘가에 넣으면 그 장소는 영영 잘못된 슬롯에 들어간다.
안 붙이면 후보에서 빠질 뿐이고, 백필 스크립트가 매번 목록으로 보고한다.
`openingHours`가 모름을 열림으로 접지 않는 것(#27)과 같은 규칙이다.
같은 이유로 `IS_FREE`가 빈 값이면 `fee:paid`로 접지 않는다.

**코드표는 저장소에 커밋한다.** `locationBasedList2`는 `cat3`을 코드로만 준다.
`A02060500`이 미술관이라는 건 `categoryCode2`를 따로 불러야 안다.
`scripts/ingest/tourCategories.json`에 140종을 받아 넣어뒀고, 회귀 테스트가
**매핑에 쓴 코드가 전부 이 표에 있는지** 검사한다. 코드를 한 글자 틀리면 아무
태그도 안 붙는데 에러도 안 난다 — 조용히 비는 게 제일 위험하다.
덕분에 백필 자체는 API 호출 0회다 (원본은 `place_sources.raw_json`에 있다).

**백필은 멱등적이다.** 여러 번 돌린다는 전제로 만들었다. `mergeFacets`가 기존
패싯을 걷어내고 다시 계산해 넣기 때문에, 매핑을 고치고 다시 돌리면 옛 패싯이
남지 않는다. 붙이기만 하는 방식이었다면 매핑을 고칠 때마다 쓰레기가 쌓인다.

**부수적으로 찾은 것: 공원 26곳이 `kind='activity'`로 들어가 있었다.**
`toKind()`가 `cat1='A01'`(자연)일 때만 park을 주는데 TourAPI의 "공원"은
A02(인문)에 있다. 산책 슬롯은 `kind='park'`만 찾으므로 서울 전체에서 산책에
쓸 수 있는 장소가 7곳뿐이었다. 파생값이 아니라 후보 조회의 1차 기준이라
태그와 같이 조용히 바꾸지 않고 `--fix-kind` 플래그로 분리해 진웅이 확인 후
적용했다. **park 7곳 → 33곳, 9개 상권 전부에 산책 후보가 생겼다.**

**백필만 하면 다음 수집 때 되돌아간다.** 두 수집기 모두 `ON CONFLICT`로
`tags_json`과 `kind`를 통째로 덮어쓴다. `seoulCulture.mjs`는 **주 1회** 도는
정기 작업이라, 수집기를 안 고쳤으면 다음 주에 403건의 패싯이 통째로 날아갔다.
그래서 수집기도 같이 고쳤다 — 두 수집기가 `mergeFacets`로 태그를 만든다.

같은 이유로 `toKind`·`toIsIndoor`를 `tourApi.mjs`에서 `shared/placeFacets.ts`로
옮겼다(`kindFromTourApi` / `isIndoorForKind`). **수집기 안에 있으면 회귀 테스트가
못 잡는다.** 공원 버그가 정확히 그래서 오래 살아남았다. 수집 스크립트에는
네트워크와 키가 필요하지만 `shared/`의 순수 함수는 테스트가 그냥 부를 수 있다.

**포기한 것**: 장르를 더 잘게 쪼개는 것. 박물관과 미술관을 나눌 수는 있지만
슬롯 배치에서는 둘 다 "실내에서 1~2시간 걸으며 보는 곳"으로 똑같이 다뤄진다.
**값 하나가 배치나 다양성 판정을 바꿀 때만 어휘에 넣는다.**
취향으로 나누고 싶어지면 그건 패싯이 아니라 점수 쪽 일이다.

## 29. 실제 장소 베타 미리보기는 정식 추천 생성과 분리한다

**결정.** 약속 조회에서 시간 골격의 장소 슬롯을 현재 `places` 후보로 채워 보여준다.
활동 슬롯은 진행 중인 기간 한정 행사·전시를 상설 활동보다 먼저 고른다. 날짜·종류·
영업시간은 점수 전에 적용하고, `closed`는 제외한다. 영업시간이 `unknown`이면 숨기지
않되 화면에 방문 전 확인 경고를 반드시 붙인다. 같은 장소는 하루에 두 번 쓰지 않는다.

**왜.** API 데이터를 모은 목적은 "활동"이라는 글자 대신 실제 행사·장소를 보여주는
것이다. 2026-08-14 성수 운영 데이터에는 서울국제정원박람회, 여름식탁 전시 등
진행 중인 후보가 이미 있는데 화면은 시간 골격만 내리고 있었다. 정식 추천 엔진이
완성될 때까지 이 데이터를 숨기면 수집 결과를 제품에서 검증할 수 없다.

**경계.** 이것은 `recommendation_requests`와 impression을 만드는 정식 추천 생성이
아니다. Q14가 열려 있으므로 알레르기·예산을 판정한 척하지 않는다. 현재 베타 조회는
한 번의 D1 후보 조회와 결정론적 선택만 수행한다. 정식 코스 저장·Cron 생성·빔서치·
학습 로그는 로드맵 8~9번에 그대로 남긴다. 소곤파일 본문은 조회도 입력도 하지 않는다.

**포기한 것.** 영업시간 미상 후보를 전부 제외해 코스를 비우는 방식. 현재 행사 데이터는
시간 원문이 없는 경우가 많아 차별화 축 전체가 사라진다. 대신 `unknown`을 `open`으로
표현하지 않고 사용자에게 그대로 드러낸다.

## 30. 핵심 취향은 홈에서 명시적으로 받고, 둘 다 끝나야 코스를 연다

**결정.** 가입·로그인 과정에는 취향 질문을 넣지 않는다. 연결된 사용자의 홈 최상단에
"아직 완벽한 추천을 못 해줘요" 카드를 두고 각자 핵심 취향 20문항을 받는다. 두 사람
모두 완료하기 전에는 실제 장소 코스를 추천하지 않는다. 완료 후에는 장소의 날짜·종류·
영업시간 하드 필터를 통과한 후보 안에서 `min(A 취향 점수, B 취향 점수)`를 먼저 비교한다.

**#26을 뒤집은 이유.** #26의 온보딩은 장소 데이터로 판정할 수 없는 분위기·거리 질문이
섞여 있었고, 가입 직후 강제했다. 지금은 `genre:*`, `cuisine:*`, `fee:*`, 실내 여부가
1,358개 운영 장소에 채워졌다. 질문을 이 실제 필드에만 한정하면 답이 곧 후보 순서를
바꾼다. 사용자가 지적한 대로 이 입력 없이 내보낸 코스는 "둘의 취향 추천"이 아니라
조건에 맞는 자동 배치일 뿐이다.

**문항 범위.** 음식 5종, 활동·장르 12종, 실내·무료·가족행사 3종이다. 운영 데이터에서
모든 피처의 후보가 1곳 이상인지 확인했다(테마파크가 최소 3곳). 장소 데이터로 안전하게
판정할 수 없는 알레르기·가격·분위기·반려동물은 묻지 않는다. 특히 알레르기는 답을
받아놓고 지키는 척할 수 없으므로 Q14가 닫히기 전까지 핵심 취향과 분리한다.

**저장.** `0006_core_preference_answers`에 문항 당시 axis/tag/weight를 보존하고 같은 D1
batch에서 `preference_signals(source='core_question')`를 갱신한다. 소곤파일 본문은
조회하지 않는다. 답은 `좋아요 / 상관없어요 / 피하고 싶어요` 세 단계이며 나중에 수정할
수 있다.

**포기한 것.** 한 사람만 답해도 상대 답을 0점으로 간주해 코스를 여는 방식. 그러면
답한 사람의 개인 추천이 되고 1:1 제품의 기준인 "둘 다 만족"을 검증할 수 없다.

## 31. 기본 코스는 남기고, 새 약속에서 장소 유형 순서를 직접 고르게 한다

**결정.** 새 약속의 시작·끝 시간을 정하면 기존 시간 골격을 기본값으로 보여준다. 사용자가
`직접 구성하기`를 누른 경우에만 식사·카페·관람/체험·산책을 1~8개까지 추가·삭제·재정렬한다.
선택한 유형 순서는 `date_plans.course_pattern_json`에 저장하고, 장소 사이에는 이동 시간을
넣은 뒤 남은 시간을 장소 수에 고르게 배분한다. 값이 `NULL`이면 기존 기본 골격을 쓴다.

**왜.** 기존 골격은 식사 시각을 중심으로 제한된 회전을 고르기 때문에, 시간이 비슷한 약속은
`밥 → 활동 → 카페 → 활동 → 밥 → 산책`으로 반복됐다. 사용자가 원하는 행사의 종류와 하루의
리듬을 표현할 입력이 없었다. 반대로 모든 사용자에게 구성을 강제하면 약속 생성이 번거로워져
기본값과 명시적 사용자 지정의 두 경로를 함께 둔다.

**경계.** 사용자가 고르는 것은 장소가 아니라 슬롯의 종류와 순서다. 실제 장소는 날짜·종류·
영업시간·예산 등 하드 필터를 지난 후보로 채우고, 소곤파일 본문은 입력으로 쓰지 않는다.

**포기한 것.** 슬롯마다 분 단위 시간을 직접 편집하게 하는 방식. 모바일에서 입력 부담이 크고
잘못된 시간표가 생기기 쉬워, 현재 L0에서는 전체 시간 창 안에서 자동 배분한다.

## 32. 추천 탭을 약속·코스의 단일 진입점으로 하고, 데이트를 기록 캘린더에 함께 놓는다

**결정.** 추천 탭에서 새 약속 생성, 기본/사용자 지정 흐름 선택, 다가오는 데이트 목록과
실제 코스를 한 화면에 보여준다. 홈의 데이트 카드는 이 추천 탭으로 들어간다. 기록 캘린더는
예정·지난 데이트와 이미 열어본 소곤파일을 같은 날짜 위에 표시한다.

**왜.** 추천 탭이 약속 화면으로 이동시키는 카드 하나뿐이면 사용자는 추천과 코스 설정을
서로 다른 기능으로 인식한다. 데이트 날짜가 `date_plans`의 1급 객체인데 캘린더에서 빠지면
기록 화면도 소곤파일 개봉일만 보여주는 반쪽짜리가 된다.

**프라이버시 경계.** 같은 날짜에서도 `데이트 약속`과 `열어본 소곤파일`은 다른 마커와 카드로
표시한다. `opened` 상태가 아닌 소곤파일 본문은 캘린더에 넣지 않으며, 데이트 약속을 보는
행위는 소곤파일 열림과 어떤 식으로도 연결하지 않는다.

**포기한 것.** 추천 탭과 별도의 약속 관리 화면을 서로 다른 UX로 키우는 방식. 같은 생성 폼과
목록을 재사용해 규칙과 화면이 어긋나는 일을 막는다.

## 33. 기본 데이트 흐름은 개인별로 받고, 공통 순서만 둘의 기본값으로 쓴다

**결정.** 추천 탭의 핵심 취향 카드 옆에 같은 크기의 `둘의 기본 코스 맞추기` 카드를 둔다.
각자는 식사·카페·관람/체험·산책을 1~8개 순서대로 따로 저장하고 상대의 전체 순서를 본다.
화면 맨 위에는 두 순서의 **최장 공통 부분 수열**만 보여준다. 공통되지 않는 부분은 자동으로
섞지 않고 둘이 조율해 달라고 명시한다. 전체 순서가 완전히 같아지면 그때 합의된 흐름을 새
약속의 기본 코스로 쓰고 `date_plans.course_pattern_json`에도 스냅샷으로 저장한다.

**왜.** 약속 하나를 만든 사람이 코스를 혼자 정하면 상대 취향이 결과에 들어오지 않는다.
종류의 단순 교집합은 순서를 잃어 `밥 → 카페`와 `카페 → 밥`을 같은 합의로 잘못 볼 수 있다.
최장 공통 부분 수열은 중복된 식사도 각각 한 번씩 소비하면서 두 사람 모두가 택한 상대 순서를
보존한다. 멤버 생성 순서로 계산 순서를 고정해 어느 계정에서 조회해도 같은 접점이 나온다.

**저장.** `0008_member_course_preferences`는 개인별 JSON 순서만 저장한다. 접점은 8×8 동적
계획법으로 조회 때 계산하며 DB에 중복 저장하지 않는다. 소곤파일 본문은 조회하지 않는다.

**포기한 것.** 두 순서를 점수로 강제 병합해 하나의 완성 코스를 자동 생성하는 방식. 어느 쪽의
차이를 버렸는지 숨기게 되므로, 합의된 접점만 자동화하고 나머지는 관계 안의 대화로 남긴다.

## 34. 기본 코스는 순서가 완전히 같을 때가 아니라 접점이 있을 때 쓴다

**결정.** 33번의 조건을 완화한다. 두 순서가 완전히 같아야(`agreed`) 새 약속의 기본 코스로
쓰던 것을, **접점(`commonPattern`)이 비어 있지 않으면** 쓰도록 바꾼다. 겹치지 않는 부분은
버린다. 다만 접점이 짧아 시간 창을 제대로 못 채우면 규칙 기반 `buildCourseSkeleton`으로
물러난다. 판정은 `shared/dateCourseSkeleton.ts`의 `resolveDefaultCoursePattern` 한 곳에
두고 화면과 서버가 같이 쓴다.

**왜 완화했나.** 완전 일치는 실제로 거의 안 나온다. 접점이 `밥 → 카페`로 이미 잡혀 있는데도
순서 하나가 달라서 기본값이 통째로 안 쓰이면, 둘이 맞춘 노력이 약속에 하나도 반영되지 않는다.
접점만 쓰면 합의한 만큼은 반영되고, 나머지는 여전히 대화로 남는다.

**왜 폴백이 필요한가.** `buildCustomCourseSkeleton`은 창을 슬롯 수로 균등 분배하느라
`SLOT_SPEC[kind].max`를 보지 않는다. 직접 고른 흐름이면 그 선택을 존중하면 되지만, 접점이
1개인데 6시간 창이면 기본값이 "카페 6시간"을 내민다. 사용자가 고르지도 않은 값이라 존중할
선택이 없다. 슬롯을 스스로 늘릴 줄 아는 규칙 기본 코스가 그 자리에선 낫다. 폴백했을 때는
화면에 이유를 밝힌다.

**어디서 채우나.** 기본 코스는 **서버**가 채운다. 화면은 직접 구성한 흐름만
`coursePattern`으로 보낸다. 그래야 "직접 구성한 흐름은 끝나는 시간이 필수"라는 규칙이 둘의
기본 코스에까지 잘못 걸리지 않는다. 화면이 기본값을 실어 보내던 동안에는, 둘이 흐름을 맞춘
순간부터 끝나는 시간을 안 적은 모든 약속이 400으로 거절됐다.

**포기한 것.** 접점 뒤에 규칙 기본 로직으로 나머지 시간을 덧붙여 채우는 방식. 합의한 부분과
자동으로 채운 부분이 한 코스 안에 섞이면 사용자가 어디까지가 둘의 합의인지 구분하지 못한다.
접점을 그대로 쓰거나 규칙 기본으로 완전히 물러나거나, 둘 중 하나만 한다.
