# 결정 기록 (ADR)

같은 논의를 세 번째로 반복하지 않기 위한 파일이다.
**설계를 바꾸려 하기 전에 여기부터 본다.** 뒤집어도 되지만, 뒤집을 때는 항목을
지우지 말고 `상태: 뒤집힘 → #번호`로 남긴다.

형식: 결정 / 이유 / 대신 포기한 것

---

## 1. 추천 수집과 서빙을 분리한다

**상태**: 확정 (2026-08-09)

요청마다 외부 API를 부르지 않는다. 배치로 긁어 D1에 정규화 저장하고, 요청 시엔 로컬만 읽는다.

**이유**: 5개 API × 300~800ms면 3초를 넘긴다. 무료 쿼터는 사용자 수에 비례해 터진다.
국내 지도/검색 API는 결과 저장에 약관 제한이 있다. 결정적으로 점수에 필요한 값(가격대,
분위기, 팝업 종료일)이 API 응답에 아예 없어서 어차피 보강이 필요하다.

**포기한 것**: 실시간성. 오늘 문 연 가게가 최대 하루 늦게 들어온다. 데이트 코스는
그 정도 지연이 문제되지 않는다고 판단했다.

---

## 2. 장소와 이벤트를 한 테이블(`places`)에 담는다

**상태**: 확정 (2026-08-09)

상시 맛집·카페와 기간 한정 팝업·전시를 나누지 않는다. `starts_at` / `ends_at`이 NULL이면 상시다.

**이유**: `recommendation_impressions`가 단일 `place_id`로 참조해야 하는데 SQLite에는
다형 외래키가 없다. 두 테이블로 나누면 로그마다 "어느 테이블의 id인가"를 들고 다녀야 하고,
학습 데이터 조인이 매번 UNION이 된다.

**포기한 것**: 이벤트 전용 컬럼의 명확함. `places`에 NULL이 많은 컬럼이 생겼다.

---

## 3. 학습은 오프라인, 서빙은 선형 결합

**상태**: 확정 (2026-08-09)

로지스틱 회귀 또는 pairwise LTR을 로컬/Colab에서 학습하고, **계수 JSON만 배포**한다.

**이유**: Workers 무료 플랜은 요청당 CPU 10ms다. 추론이 `sum(w*x)` 몇 줄이면 지연이
무시된다. 모델 배포가 파일 교체라 롤백도 쉽다. 피처가 20~40개 수준이라 딥러닝을 쓸
데이터가 애초에 안 모인다.

**포기한 것**: 온라인 학습. 모델 갱신이 수동 배치가 된다. 지금 규모에선 문제없다.

## 4. 피드백은 커플이 아니라 개인 단위로 받는다

**상태**: 확정 (2026-08-09)

`recommendation_feedback.member_id`는 NOT NULL이다.

**이유**: 점수식의 핵심이 `min(A 만족도, B 만족도)`다. 커플 단위로만 받으면 누가 만족했는지
알 수 없어서 이 항을 **영원히** 학습할 수 없다. 한쪽이 계속 희생하는 걸 잡는 게 이 제품이
풀려는 문제라서, 이걸 못 배우면 추천 기능의 존재 이유가 없어진다.

**포기한 것**: 입력 단순함. 화면에서 "우리 둘 다 좋았어요" 한 번으로 못 끝내고
누구의 반응인지 알아야 한다.

## 5. 추천 당시 피처를 `features_json`으로 통째로 저장한다

**상태**: 확정 (2026-08-09)

**이유**: 나중에 재계산하면 인과가 깨진다. 팝업이 끝나고 가격이 바뀐 뒤의 피처로
"그때 왜 저장했는가"를 학습하면 틀린 걸 배운다.

**포기한 것**: 저장 공간. 노출마다 JSON이 하나씩 쌓인다. D1 용량이 문제되면
오래된 로그를 집계 후 아카이브한다.

## 6. `places`는 물리 삭제하지 않는다

**상태**: 확정 (2026-08-09)

`DELETE /api/admin/places/:id`는 `status='closed'`로 바꾼다.

**이유**: 노출 로그가 참조하고 있고 그게 학습 데이터다. 끝난 팝업을 지웠다고
과거 추천 기록이 사라지면 안 된다. 병합으로 지는 쪽도 마찬가지로 닫기만 한다.

---

## 7. 중복 병합은 50m 자동 / 2km 사람 판단

**상태**: 확정 (2026-08-09)

정규화 상호가 같고 50m 이내면 같은 장소로 보고 409를 돌려준다.
같은 상호가 2km 이내에 있으면 `place_merge_reviews`에 쌓고 운영자가 판단한다.

**이유**: 완전 자동 병합은 "성수점"과 "성수 2호점"을 합쳐버린다. 반대로 병합을 안 하면
같은 팝업이 두 번 추천된다. 둘 다 신뢰를 잃는다. 애매한 구간만 사람이 본다.

**미검증**: 50m와 2km는 감으로 정한 값이다. 실제 데이터 200건쯤 넣어보고 조정한다.
(→ 아직 미검증. `05-open-questions.md` Q13)

**보강 (2026-08-10)**: 거리만으로는 부족했다. 병합 키에 **기간 겹침**이 세 번째 축으로
들어갔다. 같은 극장에서 다음 달에 올리는 다른 공연은 같은 이름·같은 좌표여도
다른 것이다. #15를 본다.

## 8. 후보 생성은 항상 지오해시 이웃 9칸을 조회한다

**상태**: 확정 (2026-08-09)

`geohashWithNeighbors()`를 거치지 않고 `geohash5 = ?`로 조회하는 코드를 만들지 않는다.

**이유**: 셀 하나만 보면 경계 바로 건너편 수십 m 거리의 장소가 후보에서 통째로 빠진다.
증상이 "추천이 좀 이상하다" 정도로만 나타나서 발견이 아주 늦다.
`scripts/test.mjs`가 ±4km 격자를 훑어 이걸 검증한다.

## 9. 운영자 권한은 API로 승격시키지 않는다

**상태**: 확정 (2026-08-09)

가입은 항상 `role='member'`다. `admin`으로 올리려면 D1에서 직접 UPDATE 한다.
`requireAdmin`은 권한 없으면 403이 아니라 **404**를 준다.

**이유**: 승격 API가 있으면 그게 곧 권한 상승 공격면이다. 운영자가 한 명인 동안은
수동이 가장 사고가 적다. 404를 주는 건 운영자 경로의 존재 자체를 알리지 않기 위해서다.

## 10. 하드 제약은 학습 대상이 아니다

**상태**: 확정 · 절대 규칙 (`00-product.md` 참조)

알레르기, 영업시간, 예산 상한, 최대 이동시간은 필터다. 가중치로 상쇄되지 않고
LLM이 판정하지 않는다. `preference_signals.is_hard_constraint = 1`로 분리 저장한다.

**이유**: 학습된 점수는 확률적이라 "가끔 뚫린다". 알레르기가 가끔 뚫리면 제품이 아니라 사고다.

## 11. CLI 도구는 devDependency로 고정한다

**상태**: 확정 (2026-08-09)

`wrangler`를 `package.json`에 넣고 `yarn wrangler ...`로 부른다.
전역 설치나 `npx` / `yarn dlx`를 문서에 적지 않는다.

**이유**: `BETA_DEPLOY.md`가 처음부터 `wrangler d1 execute ...`를 안내하고 있었는데,
그 도구는 전역에도 프로젝트에도 설치된 적이 없었다. 문서를 믿고 명령을 실행하면 실패하고,
사람과 에이전트 양쪽이 매번 환경부터 디버깅하게 된다. 버전이 고정돼야 어제 되던 명령이
오늘도 된다.

**포기한 것**: 설치 용량(약 200MB)과 `yarn.lock` 변경. `@cloudflare/workers-types`도
wrangler의 peer 요구(`^5.20260801.1`)에 맞춰 5.20260808.1로 함께 올렸다.

**따라오는 규칙**: 문서에 명령을 적을 때는 그 도구가 `package.json`에 있는지 먼저 확인한다.

## 12. 프리뷰 환경은 당분간 쓰지 않는다 (검증은 프로덕션에서)

**상태**: 보류 — 프로토타입 + 추천 시스템이 완성되면 다시 켠다 (2026-08-09)

Cloudflare Pages는 바인딩을 Production / Preview 환경별로 **따로** 관리한다.
지금 `DB` 바인딩은 Production에만 걸려 있고, **Preview에는 일부러 걸지 않는다.**
따라서 프리뷰 배포에서는 DB를 쓰는 모든 엔드포인트가 500이다. 이건 버그가 아니다.
PR은 머지 전 검증 없이 main으로 보내고, 프로덕션 배포에서 확인한다.

**이유**: 아직 실사용자가 0명이라 프로덕션에서 깨져도 다치는 사람이 없다.
반대로 프리뷰를 제대로 쓰려면 DB·계정·마이그레이션을 두 벌 유지해야 하는데,
지금 속도에서는 그 비용이 얻는 안전보다 크다.

**언제 뒤집나**: 실사용자가 붙거나, 남이 못 볼 데이터가 프로덕션에 쌓이기 시작하면
그때는 프리뷰 없이 머지하는 게 위험해진다. 그 시점에 이 항목을 뒤집는다.

**발견 경위**: 첫 프리뷰 배포에서 로그인이 **존재하지 않는 계정에도** 500을 냈다.
`wrangler pages deployment tail`로 보니
`TypeError: Cannot read properties of undefined (reading 'prepare')` —
`env.DB`가 undefined였다. 라우팅 자체는 정상이었다
(`/api/admin/places`가 404가 아니라 401을 돌려줬다).

**남겨둔 것**: `sogonzip-db-preview` (`e83079e6-366c-478b-8ee0-55bbad7a4586`)를
이미 만들어 0001~0003을 적용하고 운영자 계정을 넣어뒀다. 나중에 켤 때 바로 쓴다.

⚠️ **이 DB는 지금부터 스키마가 뒤처진다.** 0004 이후 마이그레이션은 여기에 적용되지
않는다. 나중에 켤 때는 **누락된 마이그레이션을 먼저 채우고** 바인딩한다.
그냥 붙이면 "프로덕션에선 되는데 프리뷰에선 안 되는" 유령 버그를 쫓게 된다.

**켤 때 할 일**: 대시보드 → Pages → sogon-zip → Settings → Bindings의 **Preview**
환경에 `DB` = `sogonzip-db-preview` 추가. 바인딩은 **다음 배포부터** 적용되므로
추가 후 반드시 재배포한다.

## 13. 데이터는 공공 API로 만들고, 팝업만 사람이 보강한다

**상태**: 확정 (2026-08-09) · 근거 문서 [`../date-course-data-strategy.md`](../date-course-data-strategy.md)

Q1(팝업 데이터)과 Q4(서비스 지역)를 함께 닫는다.

**서비스 지역**: 서울 핵심 상권 6곳 — 성수 · 한남 · 연남/홍대 · 을지로 · 잠실 · 강남/신사.
전국을 넣으면 밀도가 낮아 "도보 12분" 같은 코스가 애초에 안 나온다.

**소스를 역할별로 나눈다.** 하나의 완벽한 API를 찾지 않는다.

| 역할 | 소스 |
|---|---|
| 행사·전시 기본 | 서울 문화행사, TourAPI, KOPIS |
| 맛집·카페 장소 | 카카오 로컬 |
| 신규 팝업 발견 | 다음 웹·블로그 검색 |
| 사실 확인 | 공식 홈페이지·예약 페이지 |
| 롱테일 | 운영자 직접 등록 (`/api/admin/places`) |

**Instagram 화이트리스트는 1단계에서 뺀다.** 전략 문서는 100~300개 계정 감시를 1단계에
넣었지만, 공식 API로는 일반 계정을 읽을 수 없어 결국 스크래핑이 된다. 문서 스스로 §2에서
그게 깨지기 쉽다고 적어놨다. 공공 API로 먼저 밀도를 만들고 무엇이 부족한지 눈으로 본 뒤에
다시 판단한다.

**포기한 것**: 초기 팝업 커버리지. 팝업은 검색 발견 + 수동 입력으로만 들어오므로 한동안 얇다.

**실데이터로 수정한 것 (2026-08-10)**: "상권 6곳 바깥은 저장하지 않는다"를 뒤집었다.
서울 문화행사 19,488건 중 **아직 안 끝난 건 403건뿐이었다.** 상권 6곳 반경 1.5km로
자르면 84건만 남는다. 403건은 저장 비용이 사실상 0인데(D1 0.26MB) 버리면 319건이 사라진다.
**밀도는 저장 단계가 아니라 추천 시점의 지오해시 후보 생성에서 잡는 게 맞다.**

→ 서울 전체를 저장하고, 상권은 `area_code`로 표시만 한다. 반경은 2000m(도보 25분)로
   잡았다. 1500m면 84건, 3000m면 걸어서 40분이라 더는 상권이 아니다.

→ 상권에 **종로·삼청 / 대학로 / 명동·충무로**를 추가했다. 원래 6곳에 없었는데 종로가
   단독 1위였다(80건). 광화문·삼청동·인사동은 실제로 사람들이 데이트하는 곳이다.

**스키마는 지금 건드리지 않는다.** 전략 문서가 요구하는 `verified_at` / `expires_at`(재확인
기한) / `official_url` / `source_url` / `sold_out` 상태가 아직 없다. 하지만
`place_sources.raw_json`에 원본 응답을 통째로 저장하므로 **재검증을 실제로 구현할 때
0004에서 backfill하면 된다.** 쓰지도 않을 컬럼을 미리 만들지 않는다.

**미정**: 장소 태그 표현. 전략 문서는 가중치 축(`{mood: {emotional: 0.9}}`)을 쓰는데
`places.tags_json`은 평평한 배열이다. 실제 태깅을 시작할 때 정한다.

## 14. TourAPI는 KorService2 + 디코딩한 키로 부른다

**상태**: 확정 (2026-08-10)

두 가지를 틀리면 각각 400과 403이 나는데, 응답만 봐서는 원인을 알 수 없다.
`scripts/ingest/tourApi.mjs` 상단에도 적어뒀다.

1. **`KorService1`은 폐지됐다.** 같은 파라미터로 400을 낸다. `KorService2`를 쓴다.
2. **공공데이터포털이 주는 키는 이미 URL 인코딩된 상태다.** 그대로 쿼리에 넣으면
   이중 인코딩돼서 403이 난다. `decodeURIComponent`를 한 번 거쳐야 한다.

**수집 범위**: contentTypeId 12(관광지) · 14(문화시설) · 28(레포츠) · 38(쇼핑) ·
39(음식점). 39는 `cat3 === 'A05020900'`이면 카페, 아니면 음식점이다.

**뺀 것**:
- 15 축제공연행사 — 이 조회로는 **행사 기간이 안 나온다.** 종료일 없이 넣으면
  끝난 행사를 추천하게 된다. 서울 문화행사가 이미 덮고 있다.
- 25 여행코스 — 장소가 아니라 코스다. 코스는 우리가 만든다.
- 32 숙박 — `05-open-questions.md` Q12.

**비워둔 것**: 가격대와 영업시간. 이 조회에 없고 소개정보조회(`detailIntro2`)를
콘텐츠마다 한 번씩 더 불러야 하는데 개발계정 트래픽이 하루 1000이다.
NULL은 "미상"이라 예산·영업시간 하드 필터에서 제외되지 않는다.

## 15. 병합 키는 이름 + 좌표 + 기간 겹침. 괄호 안은 지우지 않는다

**상태**: 확정 (2026-08-10) — `05-open-questions.md` Q5를 닫는다

실데이터 1,364건에서 나온 버그다. `normalizePlaceName`이 괄호 안을 전부 지웠는데
서울 문화행사 제목은 `[주최기관] 제목 [작품명]` 형식이라 괄호가 오히려 정체성이었다.

```
[세종문화회관] 뮤지컬 [베토벤]          → "뮤지컬"
[중구문화재단] 뮤지컬 [디어 에반 핸슨]   → "뮤지컬"   ← 같은 장소로 판정
```

두 가지를 바꿨다.

1. **괄호 안 글자를 남긴다.** 지우는 건 지점 표기(`(성수점)`, `(2호점)`)뿐이다.
2. **병합 키에 기간 겹침을 넣는다.** `dateRangesOverlap`. 기간이 없는 쪽은 상시
   운영으로 보고 항상 겹치는 것으로 친다. 전략 문서 §4가 처음부터 요구하던 것이다.

**왜 "괄호가 이름의 대부분이면 남긴다" 같은 비율 규칙을 안 썼나**: 처음엔 그렇게
짰는데 실데이터에서 6건이 안 잡혔다. `[세종문화회관] 세종예술아카데미 [박인홍 작가]
스테들러와 함께하는 여행드로잉 클래스`는 괄호 밖이 길어서 비율 조건을 통과해버린다.
괄호가 부연인지 정체성인지 기계적으로 구분할 방법이 없다.

**남겨도 손해가 적은 이유**: 괄호 문자 자체는 마지막 구두점 제거에서 사라진다.
`블루보틀 (성수)`와 `블루보틀 성수`는 어차피 같은 키가 된다. 한쪽 소스가 괄호
부분을 **통째로 빠뜨렸을 때만** 갈라진다. 실데이터에 그런 쌍이 하나 있다
(`공근혜갤러리` / `[K드라마 촬영지] 공근혜갤러리`). 오탐 11건을 없애고 미탐 1건을
얻는 거래라 받았다. 미탐 쪽 대책은 Q13에 적어뒀다.

**포기한 것**: 종류(`kind`)를 병합 키에 넣는 것. 같은 자리의 카페와 음식점은
대개 같은 가게다. 넣으면 갈라진다.

**결과**: 프로덕션 병합 키 충돌 12건 → 0건. 409 오탐이 사라졌다.

## 16. 파생 값 backfill과 만료 정리는 스크립트로 둔다

**상태**: 확정 (2026-08-10)

- `scripts/ingest/renormalize.mjs` — `name_normalized`를 현재 규칙으로 다시 계산한다.
  **`normalizePlaceName`을 고칠 때마다 돌려야 한다.** 병합 키는 계산해서 넣어둔
  값이라, 규칙만 바꾸면 이미 들어간 행은 낡은 키를 들고 있고 새 장소가 옛 키와
  비교된다. #15를 적용하면서 409건을 갱신했다.
- `scripts/ingest/closeExpired.mjs` — `ends_at`이 지난 `active` 장소를 `closed`로
  바꾼다. 매일 한 번. 수집기는 끝난 행사를 새로 넣지 않지만, 넣을 때 살아 있던
  행사는 시간이 지나도 `active`로 남는다.

**되돌리지 않는다**: 종료일이 미뤄져 다시 살아난 행사를 자동으로 열면, 운영자가
손으로 닫은 장소(`DELETE /api/admin/places/:id`도 `closed`를 쓴다)까지 되살아난다.
다시 여는 건 사람이 한다.

**wrangler의 변경 행 수는 믿지 않는다**: `d1 execute --file --json`이 주는
`meta.changes`는 실제 행 수보다 크다(1행짜리 UPDATE에 2가 온다). 두 스크립트 모두
실행한 뒤 다시 SELECT해서 확인하고, 어긋나면 실패로 끝낸다.

**Cron Worker로 옮기는 건 나중이다** (`02-roadmap.md` 9번). Pages Functions는 cron을
못 돌리고 요청당 CPU가 10ms다.

## 17. 로그인·연결 상태로 라우트를 가른다. 프로필의 단일 소스는 세션이다

**상태**: 확정 (2026-08-10)

진웅이 잡았다. 다솜은 원우와 이미 연결돼 있는데 로그인 후에도 "연인 찾기"가 계속 나왔다.

원인은 두 가지였고 둘 다 고쳤다.

**1. 계정 만들기 전 화면에 가드가 없었다.** `RedirectIfAuthed`가 걸린 건 `/login`
하나뿐이라, 로그인한 사람이 주소창으로 사이트에 다시 들어오면 `/`(소개) →
`/relationship`("연인과 시작하기") → `/create-room`을 그대로 만났다.

→ `/`, `/intro`, `/relationship`, `/login`은 `RedirectIfAuthed`로 감싼다.
→ `/create-room`은 `RedirectIfConnected`로 감싼다. 여기는 비로그인(가입)과
   로그인했지만 미연결(연결 코드 입력) 둘 다 들어와야 해서 `RedirectIfAuthed`를
   쓸 수 없다. **이미 연결된 사람만** 홈으로 보낸다. 정원이 2명이라 더 할 게 없다.

**2. `syncRemoteData()`가 프로필을 갱신하지 않았다.** 파일과 취향만 받아왔다.
`HomeScreen`은 `syncRemoteData()` 뒤에 `getProfile()`을 다시 읽었는데, 그 함수는
localStorage를 읽을 뿐이라 값이 그대로였다. **상대가 연결을 수락해도 새로고침
전까지 "아직 누구와도 연결되지 않았어요"가 남는다.**

→ 화면이 프로필을 따로 들고 있지 않는다. `useSession()`이 단일 소스다.
   `HomeScreen`은 진입할 때 `refresh()`를 불러 서버에 다시 물어본다.

**따라오는 규칙**: 화면에서 `getProfile()`을 `useState` 초기값으로 쓰지 않는다.
연결 상태는 상대의 행동으로 바뀌기 때문에, 내 기기의 마지막 스냅샷은 언제든 낡았다.

## 18. 베타 추천은 친구 2~3커플에게 "실험 중"으로 연다

**상태**: 확정 (2026-08-10) — `05-open-questions.md` Q2를 닫는다

진웅 결정. 실사용 커플을 2~3쌍 모집하고, 품질이 낮다는 걸 미리 알리고 연다.

**이유**: L0 졸업 조건이 추천 품질이 아니라 **로그가 쌓이는 것**이다. 품질이
좋아질 때까지 기다리면 로그가 안 쌓이고, 로그가 없으면 품질이 안 올라간다.
기다리는 선택지는 교착이다.

**산수**: 세션 100개가 목표다. 1커플 주 1회면 2년, 5커플이면 20주다.
지금 실사용 커플은 0쌍이므로(다솜·원우는 진웅의 테스트 계정) **사람을 붙이는 것
자체가 데이터 수집의 첫 단계다.** 파이프라인을 아무리 잘 만들어도 0이 쌓인다.

**따라오는 제품 요구사항**: 점수식의 `min(A 만족도, B 만족도)`는 두 사람 반응이
모두 있어야 계산된다. 지금처럼 추천을 요청한 사람만 반응하면 이 항을 영원히
못 배운다(#4). 추천은 개인의 목록이 아니라 **소곤폴더에 놓이는 공유 객체**여야
한다 — A가 코스를 뽑으면 B의 홈에 뜬다. `recommendation_requests.room_id`가
이미 있어서 스키마 변경은 없다.

## 19. 사람 쪽 데이터보다 장소 쪽 속성이 먼저다 (온보딩을 뒤로 미룬다)

**상태**: 확정 (2026-08-10) — Q3의 순서를 정한다

원래 취향 온보딩(2지선다)을 먼저 만들려고 했다. 적재된 1,364건의 실제 필드를
세어보고 뒤집었다.

| 필드 | 실태 |
|---|---|
| 음식점 458 + 카페 107 | 태그가 `"음식점"` 하나뿐. 한식/양식/매운맛 구분 없음 |
| `price_level` | 음식점·카페 전부 NULL. 있는 건 activity 268 / exhibition 95 |
| `opening_hours` | 1,364건 전부 없음 |
| 분위기(조용한/활기찬) | 없음 |

**취향을 물어봐도 매칭할 필드가 장소 쪽에 없다.** 458개 음식점은 랭커 입장에서
거리 말고 구분되지 않는다. 온보딩을 먼저 만들면 신호는 쌓이지만 쓸 데가 없다.

→ **카카오 로컬이 먼저다.** `category_name`이 `음식점 > 한식 > 육류,고기` 형태라
   그게 곧 음식 축이다. 카카오의 값어치는 장소 개수가 아니라 **속성**에 있다.

**지금 매칭 가능한 축** (온보딩 없이도 규칙 기반 추천이 도는 범위):
종류(kind) · 실내외 · 장르 태그(전시/클래식/연극/교육체험/레포츠…) ·
무료 여부(253건) · 지역(area_code) · 기간.
"전시 + 카페 + 공원" 같은 코스는 이걸로 나온다.

**따라서 순서**: 카카오 → 추천 생성·로깅 → 온보딩 → 공유 UX.
추천 생성·로깅은 카카오에 의존하지 않으므로 활성화를 기다리는 동안 진행한다.
