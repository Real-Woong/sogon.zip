# 하루 코스 — 시간 골격과 영업시간 수집

- 작업일: 2026-08-11
- 브랜치: `main` (커밋 전)
- 기준 문서: `docs/direction/03-decisions.md` #26(접힘)·#27, `05-open-questions.md` Q14·Q18~Q20

## 1. 방향 전환

"하루종일 할 데이트 코스를 추천한다"로 범위가 잡혔다. 12:00~21:00을 설정하면
`점심 → 활동 → 카페 → 산책(비 오면 실내) → 저녁`이 시각과 함께 나오는 것.

이건 방향 전환이라기보다 **`0003`이 처음부터 가정하고 있던 제품**이었다.
`recommendation_requests`에 `start_time` / `duration_min` / `transport` /
`budget_max` / `indoor_pref` / `weather_snapshot`이 이미 있고,
`recommendation_impressions`에는 `course_slot`("코스 내 순번")이 있다.
구조는 있었고 채우는 로직과 데이터가 없었다.

## 2. 취향 온보딩을 접었다

같은 날 오전에 만든 온보딩 16문항을 되돌렸다 (`03-decisions.md` #26).

문항이 전부 *속성*(음식 종류·실내외·분위기)을 물었는데 그건 **순위 매기기**
문제의 입력이다. 하루 코스는 **일정 짜기** 문제라 필요한 입력이 다르다 —
언제, 어디서, 얼마. 셋 다 취향이 아니라 그날의 설정이라 프로필이 아니라
약속에 붙어야 한다.

실제로 필수 6문항을 지금 데이터에 대보면 절반이 죽어 있었다.

| 문항 | 상태 |
|---|---|
| 동네 | 살아 있음 — `area_code`가 후보 격자를 좁힌다 |
| 종류 | 살아 있음 — `kind`는 1,364건 전부에 있는 유일한 속성 |
| 음식 성향 | `cat3` 백필 후에나 |
| 실내/실외 | 약함 — `is_indoor`가 실측이 아니라 `kind`에서 유도한 값 |
| 이동 거리 | **죽어 있음** — 출발지를 저장하는 데가 없어 계산 불가 |
| 분위기 | **죽어 있음** — 장소 쪽 대응 데이터 0 |

## 3. 만든 것

### `0005_date_plan_window.sql`

`date_plans`에 `end_time` · `origin_area` · `budget_per_person`.
예산은 **식사에서만 못 거른다** — `price_level`이 음식점 0/458 · 카페 1/108인데
활동은 268/543, 전시는 95/223이 있다(서울 문화행사의 `USE_FEE`). 하루 예산의
큰 몫이 식사라 실질적으로는 반쪽이다. 그래도 받는 이유는
코스 카드에 예상 금액을 보여주고, 나중에 가격 데이터가 들어왔을 때 소급할 수
없는 "그때 얼마로 잡았나"를 지금부터 남기기 위해서다. 거르는 척은 하지 않는다.

`0005` 번호는 접은 온보딩 마이그레이션이 쓰던 번호다. 프로덕션에 적용한 적이
없어서 그대로 다시 쓴다.

### `shared/dateCourseSkeleton.ts`

시간 창을 슬롯으로 나눈다. 장소는 채우지 않는다.

```
12:00-13:30  90분  점심
13:30-13:45  15분  이동
13:45-15:45 120분  활동
15:45-16:00  15분  이동
16:00-17:00  60분  카페
17:00-17:15  15분  이동
17:15-18:35  80분  활동
18:35-18:50  15분  이동
18:50-20:20  90분  저녁
20:20-21:00  40분  여유
```

- **식사는 시계에 못 박는다.** 점심은 11:30~13:30 사이에서만 시작하고,
  저녁은 창의 **끝에서 역산**해 40분 여유를 남긴다.
- **서비스 시간대 08:00~23:00은 임시 가정이다.** 영업시간이 전부 NULL이라
  이게 없으면 00:00~12:45 창에 02:15 카페가 들어간다 (Q20).
- **날씨는 시간대별로 판정한다.** 오후에만 비 오는 날에 오전 산책까지 죽이면
  안 된다. 산책 슬롯만 종류를 실내로 바꾸고 나머지는 `preferIndoor`만 세운다 —
  필터가 아니라 힌트다. 예보는 `HourlyWeather`(시각·강수확률·기온)라는 자체
  형태로 받는다. 어떤 API를 쓰든 이 모양으로 바꿔 넣으면 된다.

### `shared/openingHours.ts`

`isOpenDuring`이 `'open' | 'closed' | **'unknown'**` 셋을 돌려준다.
**모름을 열림으로 접지 않는다.** 접으면 문 닫은 가게로 사람을 보내고,
닫힘으로 접으면 후보가 0개가 된다. 둘 다 틀렸다.

파싱도 같은 원칙이다. "평일 09:00~18:00, 주말 10:00~17:00"은 **읽지 않고**
`parsed: false`로 두고 원문을 남긴다. 평일 시간을 주말에 적용하면 일요일에
닫힌 가게를 열려 있다고 말하게 된다.

### `scripts/ingest/tourApiDetail.mjs`

영업시간을 채운다. 두 가지를 의도적으로 다르게 했다.

1. **필드명을 하드코딩하지 않는다.** detailIntro2는 콘텐츠 타입마다 필드
   이름이 다르다(`usetime`, `opentimefood`, `usetimeculture` ...). 이름을
   패턴으로 훑고, `--sample`로 **실제 응답 키를 먼저 눈으로 본다.**
2. **원본을 통째로 저장한다.** `place_sources`에 `source='tourapi_detail'`로.
   하루 1000건 제한이 있는 이상, 파싱을 고칠 때마다 다시 부르는 건 불가능하다.

재개는 자동이다 — detail 행이 이미 있으면 건너뛴다.

## 4. 전수 검사가 잡은 것

시간표에 구멍이 없는지는 **눈으로 못 잡는다.** 손으로 확인한 6개 케이스는
전부 멀쩡했는데, 모든 시간 창을 훑으니 **2,046개 중 481개가 깨져 있었다.**

세 가지 버그였다.

1. **꼬리 유실** — 06:00~10:00이 09:45에 끝났다. 마지막 자투리가 25분 미만이면 버려졌다
2. **앵커 앞 구멍** — 11:00~13:00에서 11:00~11:30이 통째로 비었다
3. **`break`가 너무 이름** — 활동(최소 60분)이 안 들어가는 자리에서 카페(최소 30분)도
   시도하지 않고 끝냈다. 60분이 통째로 "여유"가 됐다

지금은 2,781개 창 전부에서 구멍·겹침 0, 가장 긴 빈 시간 40분이다.
이 전수 검사가 `scripts/test.mjs`에 회귀로 들어가 있다.

## 5. 확인한 사실 두 가지

**TourAPI가 주는 3단계 분류(`cat1/cat2/cat3`)를 버리고 있다.**
`tourApi.mjs:174`가 대분류 이름만 태그로 남긴다. 결과적으로 961건의
`tags_json`이 `kind`와 완전히 중복이고 정보량이 0이다. `toKind()`는 이미
`cat3`를 읽고 있다(`A05020900`이면 카페) — 파싱은 하는데 저장을 안 한다.

**백필에 API 호출이 0번 필요하다.** `place_sources.raw_json`에 원본 응답이
통째로 있다. `cat1/cat2/cat3`는 이미 프로덕션 D1 안에 있다.
